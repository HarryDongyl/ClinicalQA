## 1. 需求分析（requirements analysis）

**目标**：把作业要求转成可以测量的行为和交付物。

**作业要什么**：对一份就诊记录（encounter note）加一张结构化表格（structured table），回答一个临床问题，并通过 SFT 让模型做到四件事：
1. **抽取**（extract）：从病历或表格中取出事实；
2. **简单数值推理**（numeric reasoning）：比较、相减、判断是否超过阈值；
3. **工具使用**（tool use）：
   - 判断**什么时候**该调用 `unit_convert` 或 `calculate_bmi`；
   - 生成**有效的**参数，其中包括隐含的英制转公制换算（imperial → metric），因为 gold 参数一律是公制；
   - 在答案中用上工具返回的结果；
4. **表达不确定**（state uncertainty）：信息缺失时说明清楚，**不编造**（no hallucination）。

**交付物**（deliverables）：
- 数据格式化流程（formatting pipeline）；
- 训练脚本；
- 数据质量分析：至少 5 个格式化样例，以及各项统计；
- 评估脚本：必须报告作业指定的五个指标；
- 一份报告：环境搭建、运行命令、硬件、产出物位置、尝试过什么、结果、局限。

**评分权重**：数据格式 10%、**微调设置 40%**、评估 10%、代码质量 20%、延伸部分（stretch / going beyond）20%。

**决策**

| 决策 | 逻辑 |
|---|---|
| 把"test 不能参与训练"扩展为**"test 不能参与任何选择"**（no selection on test） | 用 test 来选 checkpoint、阈值或超参数，和直接用 test 训练一样，都是泄漏 test 的信息（leakage） |
| 按作业原文的四个问题拆解工具使用：该不该调用（decide to call）、工具选对没有（correct tool）、参数是否有效且有依据（valid, grounded arguments）、答案是否用上结果并附简短临床说明（incorporate with brief clinical context） | 失败必须能定位到具体是哪一步出错 |
| "校准"（calibrated）首先理解为**行为上的校准**（behavioural calibration）：缺信息时拒答（abstain），信息足够时不过度拒答（over-refuse）。概率意义上的校准只作诊断 | 作业原文写的是 "explicitly stating uncertainty"，指的是一种行为 |
| 每题最多调用一次工具 | 所有 gold 的 `tool_call` 样本都恰好只调用一次 |
| 先完成 Core，再做 Stretch | 作业原文："Complete the Core track first" |

**核心矛盾**（central tension），也是整个项目的主线：
- 训练模型积极、可靠地调用工具，它就容易在输入缺失时也去调用，并编造参数；
- 让模型变得谨慎，它又会在该调用时不调用。

所以**每次评估都同时看两边**：输入缺失时是否拒答，**以及**输入完整时是否正确调用。

**可能的追问**
- "最难的需求是哪个？" → 上面的调用与拒答之间的矛盾。
- "你怎么把 calibrated 变成可以测量的东西？" → 用行为指标衡量，再加上诊断性的置信度分析（第 13 阶段）。
- "作业建议 4 小时，你花的时间远远不止，为什么？" → Core 部分很早就做完了，之后的时间主要投入在评估的可信度，以及一个数据策略上的发现，这对应 20% 的"going beyond"。照实说即可。

## 2. 约束与成功标准（constraints & success definition）

**目标**：在做任何实验之前，先定好边界和"什么算成功"。

| 方面 | 选择 | 证据或理由 |
|---|---|---|
| 硬件 | 单张 24GB GPU，因此用 4B 模型加 QLoRA | 在 RTX 4090 上实测显存峰值 7.8GB |
| 数据纪律（data discipline） | train 只用于训练；val 只用于选择；test 只在最后跑一次，而且模型清单要先冻结并提交（frozen, committed list） | 防止信息泄漏和反复使用 val 导致的过拟合（adaptive overfitting） |
| 可复现（reproducibility） | 用 uv lockfile 固定依赖；每个 run 都记录代码、数据、prompt、模板、工具 schema 的哈希（hashes）；种子 42；贪心解码（greedy decoding） | 每一个比较都能追溯到具体原因 |
| 成功标准 | 五个指定指标，**加上**行为指标：过度调用（over-call）、过度拒答（over-refusal）、编造（fabrication） | 只看五个指标，一个从不调用工具的模型也能拿到"不编造"的好分数 |
| 选择规则 | 在看到结果之前写好：选哪个 checkpoint、门槛（gates）是什么、和谁对比（comparator） | 避免赢家诅咒（winner's curse）和事后挑选（post-hoc choice） |
| 统计上的谦虚 | val 只有 250 条，单个题型的最小可检测差异（minimum detectable effect, MDE）约 14–23 个百分点，比如 numeric 只有 50 条，MDE 约 20pp | 不根据单个题型上的小差异做决策 |

**为什么用贪心解码**：
- 配对比较（paired comparisons）里没有采样噪声；
- 这些任务都有唯一的正确答案，要的是最可能的输出（mode）；
- 每题只生成一次，评估成本低；
- 只有在 greedy 下，"第一个 token 是调用的概率"才是有意义的诊断。

**代价**：
- 只能看到概率最高的那一条轨迹（trajectory），部署时如果用采样，可能会暴露出 greedy 没碰到的编造；
- 没有基于自洽性的置信度（self-consistency confidence）；
- 不同 GPU 内核（kernels）下的输出不一定逐位相同。

**事后反思**：第一波事先登记的规则后来被证明是错的（见第 7 阶段）。我们公开记录了原因，替换了规则，新规则只用于之后的实验。**规则可以改，但只能在看到它要评判的结果之前改。**

**可能的追问**："事先登记不会太死板吗？""为什么不从 train 里多划一些数据做验证？"（作业要求必须原样使用给定的划分，val 本来就小；应对办法是配对比较和有针对性的探针。）

## 3. 数据分析（data analysis）

**目标**：在格式化和训练之前，先摸清数据及其缺陷。

**做了什么**：
1. 把提供的文件逐字节复制（byte-identical copies），记录 SHA-256，每次使用前重新校验；
2. 检查数据结构（schema validation, Q1）；
3. 按 split 做统计；
4. 做 19 项针对性的质量检查（Q1–Q19）。

自动生成的报告是 `reports/data_analysis.md`，所有被标记的样本在 `reports/quality_flags.jsonl`，共 624 条。

**证据：基本统计**
- 三个 split 分别是 2000 / 250 / 400 条；
- 题型分布在每个 split 都是 40/20/25/15（val 是 40/20/24.8/15.2）；
- train 里的工具调用：BMI 410 次，单位换算 90 次；
- 410 次 BMI 调用里，有 112 次来自英制病历；
- token 长度：p50 1375，最大 1614。

**证据：质量检查**（train / val / test）

| 检查 | 发现 | 处理 |
|---|---|---|
| **Q5 参数是否有依据（argument grounding）** | **534 次 BMI 调用里有 95 次（78 / 7 / 10）**，身高体重在病历、表格、问题里都**找不到**，gold 参数是编出来的 | 影响最大的问题。用这些数据训练，会教模型编造参数（第 9–11 阶段） |
| Q5 的补充发现 | 有 67 条 BMI 样本的身高体重只出现在**问题**里。它们和上面 95 条**不重合**，因为问题也算输入的一部分 | 保留。prompt 写明了要依据问题中明确给出的数值（explicit values in the question）。P1 探针会排除这类题 |
| Q6 英制换算的舍入（imperial rounding） | 51 个身高换算回厘米后和 gold 对不上；138 个英制样本里，有 20 个用精确换算会让 BMI 差 ±0.1 | 打分时用容差处理，不改标签 |
| Q7 病历里写的 BMI 和身高体重对不上 | 119 份病历 | 保留，gold 用的是计算值 |
| Q10 算术检查 | 最初的报错其实是解析器（parser）的误报 | 修复解析器、加回归测试（regression tests），样本保留 |
| Q11 引用了外部参考范围（external reference ranges） | 46 条 extractive 答案引用的标准范围在输入里找不到 | **这是任务设计本身（task design），不是噪声**：输入没给范围时，只能用标准范围 |
| Q13 µ 和 μ 混用 | 56 条 | 统一单位写法 |
| Q16 合成数据里不合理的数值（synthetic plausibility） | 219 条 | 保留，在报告里说明 |
| Q3 / Q18 split 之间是否泄漏 | 无 | — |

**原则**：启发式检查（heuristics）只产出**候选**（candidates），不能当作 gold 有错的证据。每一项都要事先说清楚是保留、标记还是剔除（keep / flag / exclude）。

**事后反思**：有些问题**只能通过训练后的模型行为才发现**。所以数据分析要在训练之后再做一轮：
- 过滤掉 Q5 之后，"身高体重都缺失"的训练样本只剩 **1 条**（第 10 阶段）；
- 过敏类问题里，问题中明确提到过敏的训练样本有 51 条，没提到的只有 **5 条**；val 上两者的准确率分别是 36/36 和 8/18（第 10 阶段）；
- 表格自带的 eGFR 无法用肌酐、年龄、性别算出来，差异的中位数是 26–37（第 14 阶段）。

**可能的追问**
- **"你怎么确定那 78 条是 gold 错了，而不是你的解析器漏掉了？"**
  1. 检查覆盖了病历、表格**和**问题，并且考虑了磅转千克（lb→kg）、英寸转厘米（in→cm）的换算；那 67 条信息只在问题里的样本被正确地**判为有依据**，说明检查不是机械地找数字；
  2. 每一条被标记的样本都经过逐条审核（`reports/w3/q5_review_packet.md`）；
  3. base 模型在全部 7 道 val Q5 题上都选择拒答；
  4. 解析器有回归测试。
- "为什么不直接修正标签？" → 见第 9–11 阶段。

## 4. 输入输出表示（input/output representation）

**目标**：精确确定模型看到什么、输出什么，并保证训练和推理完全一致（train/inference parity）。

| 决策 | 逻辑或证据 |
|---|---|
| 使用 Qwen **原生的聊天模板**（native chat template）和原生的 `<tool_call>{"name","arguments"}</tool_call>` 格式，通过 `apply_chat_template(tools=...)` 渲染 | 和模型后训练时的格式一致，是工具调用最强的先验（prior） |
| 用户消息的结构固定：`## Encounter note` → `## Table (type)`（Markdown 表格，竖线要转义，空单位写成 `(no unit)`）→ `## Question` | 格式一致，节省 token。读表格不是瓶颈：v2.1 下 SFT 模型的 extractive 是 0.99–1.00，零样本的 base 模型也有 0.92–0.98 |
| 所有样本都提供相同的工具 schema，包括不需要调用工具的题型 | 让模型学的是**什么时候**调用，而不是"有没有工具可用" |
| 题型标签（answer_type）只放在单独的 sidecar 文件里，并有测试防止标签泄漏（label leakage） | 模型不能看到标签 |
| 调用那一轮内容为空；工具结果放在 `tool` 消息里（渲染为 `<tool_response>`）；之后是最终答案 | 这是模型原生的轨迹格式 |
| **只对 assistant 部分计算 loss**，用前缀差分（prefix-diff）的方法自己生成掩码，没有用 TRL 的 `assistant_only_loss` | 原始的 Qwen3 模板没有生成标记（generation markers），TRL 自己也把 Qwen3 列为需要打补丁的模板。掩码审计（mask audit）结果：2000/2000 条对话全部正确，5.5% 的 token 参与监督；调用那一轮的 `</tool_call><|im_end|>` 也在监督范围内 |
| 训练和推理只用同一个 `render()`；rollout 中模型的调用会用同一个模板重新渲染 | 从机制上保证训练和推理一致 |
| system prompt v1：依据输入作答、工具使用规则、信息缺失时怎么做、"过敏史缺失不等于没有过敏"、最终答案要简洁 | 冻结，并把哈希记录进每个 run |
| 训练目标直接用 gold 的公制参数，英制换算由模型隐式学会 | 遵循数据集的约定。显式的换算链（conversion chain）留作单独的消融实验（ablation） |

**可能的追问**："表格为什么不用 JSON？"（没有证据表明表格是瓶颈。）"为什么不在调用前写推理？"（见第 10 阶段的 R-VIS 消融。）"结束符有没有参与训练？"（有，掩码审计确认过。）

## 5. 模型与训练设置（model & training setup）

**目标**：一套合理、有依据、可复现，并且一张 GPU 放得下的微调配方（recipe）。

| 选择 | 取值 | 逻辑或证据 |
|---|---|---|
| 基座模型（base model） | Qwen3-4B-Instruct-2507，固定 revision | 原生支持工具调用；非思考版本（non-thinking），掩码简单；24GB 放得下；零样本时调用决策的 AUROC 已经有 0.966 |
| 方法 | **QLoRA**：NF4 量化，bf16 计算；LoRA r16 / α32 / dropout 0.05，作用于全部 7 个线性投影层（linear projections），约 33M 参数 | 全参数微调约需 64GB：bf16 权重 8GB + 梯度 8GB + fp32 主权重 16GB + Adam 状态 32GB。bf16 LoRA 约需 13GB；选 QLoRA 是为了留出余量（headroom），方便以后换更大的模型或加大 batch。QLoRA 论文指出：只要覆盖了所有线性层，rank 的影响很小 |
| 优化 | lr 1e-4，cosine 调度，3% warmup，2 个 epoch，micro-batch 1 × 梯度累积 16（共 250 步），weight decay 0，梯度裁剪 1.0，开启梯度检查点（gradient checkpointing） | QLoRA 的常规取值范围 |
| loss | **按 token 平均的交叉熵**（token-mean cross-entropy），在梯度累积时用 `num_items_in_batch` 做归一化 | HF 修复梯度累积 bug 之后的标准做法 |
| 种子和溯源（provenance） | 种子 42；每个 run 记录 git commit、依赖包版本、硬件和各项哈希 | 作业的可复现要求 |

**证据：各题型在梯度中的占比**（按监督 token 估算）

| 题型 | 样本占比 | 梯度占比 |
|---|---|---|
| extractive | 40% | 约 16% |
| numeric | 20% | 约 23% |
| uncertain | 15% | 约 20% |
| tool | 25% | 约 41%，其中调用那一轮约占 10% |

没有采用重新加权（re-weighting）。原因是占比偏低的部分（extractive 和调用决策）其实已经学会了；numeric 的错误属于推理错误，不是梯度不够。也没有经过验证的研究支持"在工具 SFT 中给调用 token 加权"。

**证据：micro-batch 的选择**。第二波试过 micro-batch 4 × 累积 4：
- 每个优化步**慢了 32%**（13.5 秒对 10.2 秒），显存 17.75GB 对 7.8GB；
- loss 曲线和 micro-batch 1 几乎完全重合：第 1、10、20 步分别是 1.915 / 0.858 / 0.582，对比 1.918 / 0.867 / 0.583。

这**直接证明了 loss 的归一化是正确的**。变慢的原因推测是 padding 让 SDPA 退回了较慢的内核，这一点还只是假设；真正的解决方法是不做 padding 的打包（padding-free packing）。

**可能的追问**："bf16 LoRA 放得下，为什么还用 QLoRA？"（为了留余量；量化对精度的影响没有测过，bf16 对照已经写进下一步。）"调过 r 吗？"（没有，依据是文献加上 train-fit 诊断。）"为什么 micro-batch 用 1？"（见上面的实测数据。）

## 6. 评估设计 v1（evaluation design v1）

**目标**：一个能运行的评估流程，报告五个指标，并且能定位失败原因。

**做了什么**：
- **rollout 状态机**（rollout state machine）：生成 → 严格解析，格式错误的 JSON 一律不修复 → 按 schema 校验 → **真正执行工具**（real execution）→ 把结果交回模型 → 生成最终答案。
- 预算（budget）：最多 1 次调用、2 轮 assistant、每轮 256 个 token、总共 512 个；贪心解码；左侧 padding。
- 每条轨迹记录：原始输出、解析出的调用、执行器的输入和输出、停止原因、每个 token 的 log-prob、第一个 token 是 `<tool_call>` 的概率。
- **v1 打分器**（基于正则）：
  - extractive：gold 中的数字要以同样精度出现，同一句里要有方向词，否则退回到 token-F1；
  - numeric：比对 gold 中的数字；
  - 工具：按"选对工具 → 格式有效 → 参数在 ±0.05 以内 → 执行成功 → 结果写进答案"逐步判断（tool funnel）；
  - uncertain：要有拒答措辞，点名缺失的字段，并且没有编造数值。
- 额外的诊断：工具端到端成功率（tool E2E）、过度调用、过度拒答、无依据参数率；Wilson 置信区间；配对 bootstrap。
- test 的保护：`generate` 命令拒绝在 test 上运行；`final` 命令要求工作区干净，而且 adapter 必须是事先冻结的那个。

**可能的追问**："为什么真正执行工具，而不用 teacher forcing？"（这样测的才是部署时的行为：决定、参数、有没有用上结果。）"为什么不用 LLM 当裁判（LLM judge）？"（先保证确定性和低成本；等确定性打分的局限摸清之后再考虑，见第 8 阶段。）

## 7. 第一波（wave 1，RunPod RTX 4090）

**目标**：第一个端到端结果。SFT 有没有用？

**做了什么**：3 组配置 × 2 个 epoch：raw 数据 lr 1e-4、raw 数据 lr 5e-5、Q5 过滤后的数据 lr 5e-5。按事先登记的规则选模型：在 val 中去掉 Q5 题之后的子集上，取 v1 的 macro 分。选中的是 **raw lr 1e-4 的 epoch 1**（macro 0.878），然后只在 test 上评估一次。

**证据**
- test 上 v1 macro：base **0.442** → SFT **0.824**。
- 成本：训练约 44 分钟，每步约 10 秒，显存峰值 7.8GB。
- 调用决策：第一个 token 的 AUROC 从 0.966（base）升到 **1.000**（SFT）；区分 tool 题和 uncertain 题的 AUROC 从 0.859 升到 1.000。
- **7 道 val Q5 题**：
  - raw SFT 有 6/7 **编造参数**，调用概率约 0.99，而且反复写出同一个记住的身高 **178.5 cm**；
  - base 和过滤后的模型都是 7/7 拒答。
- test 上剩下的工具错误：6 次英制换算偏差 0.1–0.2，比如 241.8 lb 被换算成 110.0 kg，而 gold 是 109.7；val 上没有这类错误。
- **v1 打分器的审计**：
  - base 在 extractive 上的 61 个"错误"里，约 **58 个是误判**（false negatives），答案其实对，只是写法不同；
  - SFT 在 numeric 上的错误，约一半是误判。

**决策**
- 认定选择规则有缺陷：它只在去掉 Q5 的子集上打分，所以**看不到**模型会编造，结果恰好选中了会编造的那个。
- v1 打分器不能用来下题型层面的结论，必须重建。

**事后反思**：0.44 → 0.82 这个结果里，相当大一部分是 v1 在奖励"和 gold 写法相似"，而不完全是能力的提升。

**可能的追问**："那 SFT 到底有没有用？"（有，在工具使用、拒答和格式上提升明显而稳定；extractive 本来就基本会了，见第 8 阶段。）"你怎么会选中一个会编造的模型？"（因为选择规则的盲区。）

## 8. 重建 scorer（rebuilding the scorer）

**目标**：做一个衡量"答案对不对"、而不是"像不像 gold"的评估，并且要经过独立判断的验证。

**调研**（查阅了原始代码，确认过文件路径）：

| 来源 | 借鉴的做法 |
|---|---|
| MedCalc-Bench `evaluate.py` | 答案键（answer keys）从输入计算出来；小数结果用上下限容差带（lower/upper tolerance band）；整数和分类结果要求完全一致 |
| DROP `drop_eval.py` | 数字门槛（number gate） |
| BFCL `ast_checker.py` | 允许多个可接受的答案（possible answers）；"该不该调用"（relevance）和解析错误单独统计 |
| τ-bench | 按执行后的结果打分（score the executed outcome） |
| AbstentionBench | 关键词检测器和 LLM 裁判可以互换使用 |
| HealthBench | 逐条二值打分的细则（binary per-criterion rubric）；有一套检验裁判和医生是否一致的元评估（meta-evaluation） |

你那版有边界的 v2（bounded v2）有 25–42% 的样本进入"待复核"（review），无法用来给模型排序。

**v2.0 的设计**：
- 仿照 MedCalc，**在读取任何预测之前**就从表格、问题、病历计算出答案键；
- 按题型做检查（typed checks）：数值、状态、差值、比值、百分比、BMI、实体（entity）、集合（set）、是非（yes/no），最后有一个文本兜底（text fallback）；
- 容差策略：整数完全一致；差值 ±max(0.051, 0.5%)；比值和百分比 ±5%；BMI ±0.15；
- 能处理否定的状态读取器（negation-aware state reader），可以跨句子关联；
- 工具题按执行结果打分；Q5 题期望拒答；
- gold 自检（gold self-check）的通过率在开发过程中从 90.2% 提升到 98%。

**验证流程**：
- 盲评（blinded）的 LLM 评审，按书面细则打分，看不到 scorer 的结果，也不知道是哪个模型；
- 每个评估集由两组评审独立标注；严格组的评审必须引用具体数值；
- 发现并剔除了一个敷衍的评审（71 条用了同一句理由）；
- 每次在干净的 holdout 上验证之前，先用 sha256 冻结 scorer。

| scorer | 开发集（调过规则） | holdout 1（test） | holdout 2（test，从未见过） |
|---|---|---|---|
| v1 | 65.8%（κ 0.17） | 67.5%（κ 0.34） | **65.7%（κ 0.26）**，35 条误判 |
| v2.0 | 99.2% | **76.7%（κ 0.48）**：在开发集上过拟合了 | — |
| v2.1 | 100% | 95.0%（在 holdout 1 上调过） | **92.6%（κ 0.72）** |

评审之间的一致性（rater agreement）：0.92 / 1.00 / 0.93。

**证据：用 v2.1 重新看第一波**：
- base 的 extractive 从 0.39 变成 0.92–0.98，说明 base 本来就会读表格；
- SFT 真正稳定的提升在**工具使用**（base 0.57–0.74，SFT 0.87–1.00）、拒答和格式上。

**事后反思**：
- **方法上的亮点**：照实报告 76.7% 这个 holdout 结果，然后按题型做通用修复，再在第二个从未见过的 holdout 上重新验证。
- **仍然存在的弱点**：两层解析都是贴合这个数据集模板写的正则规则，numeric 答案仍然会被判得偏宽（见第 11 阶段）；具体机制见第 17 阶段。

**可能的追问**："谁来验证你的评审？"（是带防护措施的 LLM 评审，加上我非正式地人工抽查了约 20 条，但没有留下记录。）"92.6% 是不是也过拟合了？"（这是在从未见过的样本上测的；holdout 1 上调规则带来的偏差无法精确量化，已在报告中说明。）

## 9. 第二波（wave 2：学习率、batch、prompt）

**目标**：在现有配方内调参，并测试用 prompt 修正参考范围错误的办法。

| 实验 | 证据 | 解读 |
|---|---|---|
| 在过滤后的数据上扫学习率 1e-4 / 1.5e-4 / 2e-4（v2.1 macro，ep1 / ep2） | 0.936 / 0.914，0.931 / 0.921，0.908 / 0.941 | 差异都在 0.03 以内，属于**噪声** |
| micro-batch 4 | 见第 5 阶段 | 更慢，优化效果相同；主动停掉 |
| prompt v2（在 v1 上加一句"只使用输入中给出的参考范围"），只在推理时替换 | 配对比较中每个题型只有 0–2 条结果改变，CI 全部包含 0；这一句针对的 numeric 只多对了 1 条 | SFT 模型对 prompt 的小改动不敏感；而且这一句和 36 条正确的训练 gold 相矛盾（Q11） |
| **所有 run 在自然 Q5 题上的行为** | raw：**50/56 通过调用编造（89%）**；过滤后、lr 5e-5：1/28；**过滤后、lr ≥ 1e-4：17/42 在正文里编造**，比如写"The patient's weight is documented at 68.5 kg…"，但根本没有调用工具 | 过滤去掉了错误的信号，但没有教会正确的行为；编造**转移到了正文里**，学习率越高越严重 |

**事后反思**：第一波得出"过滤就能解决问题"的印象，是在 lr 5e-5 下测的。数据上的决策必须在**实际要用的学习率**下检验。

**可能的追问**："为什么不继续调参？"（差异在噪声范围内，继续扫参只会加重赢家诅咒；多跑几个种子比找"最佳学习率"更有价值。）

## 11. 第三波（wave 3，RTX 4090，单个种子）

**目标**：检验改标策略和各个基线。

**设置**：
- **P1 探针**：34 对冻结的探针。来源是 val 中 40 道有依据的 BMI 题，去掉 6 道"问题里直接给出了测量值"的，剩 34 道。每一对包括：
  - 删掉身高和体重的版本，正确行为是拒答；
  - 原始的完整输入（intact partner），正确行为是调用工具。
- **各组配置**：
  - C-filtered：1922 条，242 步；
  - **F-relabel**：2000 条，250 步；
  - R0-v1 / R0-v3 / R0-v3-FS4；
  - R0-8B（零样本）。

**证据：缺数据时的行为（主要结论）**

| 配置 | P1 编造（调用中 / 正文中） | 完整输入时正确调用 | 有依据的工具题 /55 | 自然 Q5 编造 /7 |
|---|---|---|---|---|
| R0-v1 | 0/34 | 20/34 | 29 | 0 |
| R0-v3 | 0/34 | **5/34** | **9** | 0 |
| R0-v3-FS4 | 2/34 | 21/34 | 29 | — |
| **C-filtered** | **25/34（0 / 25）** | 33/34 | 54 | 4 |
| **F-relabel，ep2** | **0/34**（Wilson 上限 10.15%） | **33/34**（同一条失败，val_105） | 54 | **0** |
| R0-8B | **28/34（28 / 6）** | 25/34 | 46 | — |

从这张表可以读出：
1. **改标解决了缺数据的问题，而且没有牺牲工具调用**。
2. **只做过滤的模型在正文里编造**；如果只看调用相关的指标，这 25 例会全部漏掉。
3. **prompt 工程做不到**：
   - 强 prompt 反而让工具调用变差：40 道 BMI 题里有 32 道、15 道换算题里有 11 道没有调用工具；
   - 加 few-shot 后只恢复了 BMI 的工具选择（33/40，其中 6 次参数错误），换算题只有 4/15，因为示例里只有一个 BMI 的例子。
4. **base 模型的"零编造"其实是因为它很少调用**。
5. **8B 基座调用得很积极，参数却是编的**，所以单靠模型规模解决不了依据性的问题。

**证据：其他指标**
- v2.1 macro：R0-v1 73.8%、v3 67.0%、FS4 77.6%、C 91.4%、F ep1 94.4%、**F ep2 96.7%**、R0-8B 68.8%。
- F 对 C 的配对比较（探索性，未做多重比较校正）：v2.1 +5.28pp，CI [2.22, 8.67]；v1 +3.07pp，CI [0.25, 6.23]。
- **numeric**：v2.1 下从 C 的 40/50 变成 F 的 46/50，但**这 6 个表面上的提升里只有 3 个可信**：
  - 可信的：val_028（TIBC）、val_114（血细胞比容）、val_186（胆红素的排序）；
  - 不可信的：val_054（题目有歧义）、val_062（前后矛盾，属于误判为正确，false positive）、val_124（scorer 偏好某种措辞）；
  - 还有其他被误判为正确的：val_239（多写了一句关于 ALT 的错误陈述）；
  - 仍然存在的真实错误：val_001、085、185、202（把 119.3 写成了 19.3）。
  - **numeric 目前没有可靠结论**。
- 训练：42.7 / 43.9 分钟，显存 7.81 GiB。
- teacher-forced 的 val loss：**F（0.3470）反而比 C（0.3414）差，但行为更好**，说明在这里交叉熵不适合用来选模型。
- train-fit 上的 numeric（v1）：C 32/50，F 34/50。受打分器影响，不能据此判断模型容量是否不够。
- C10a 回答置信度的 AUROC：C 0.750，F 0.640。两者的错误集合不同，所以不能说"F 的校准变差了"。C10b 调用决策的 AUROC 两者都是 1.0。
- 成本：FS4 的 prompt 有 4484 个 token，SFT 是 1294 个，但 FS4 实测**并没有更慢**（846 秒对 1001 秒），所以不能说 SFT 有延迟优势。

**决策**：
- F ep2 是目前单种子下最好的候选；
- 对比用的 prompt 继续是 v1；
- v3 和 FS4 不采用；
- numeric 需要做逐条结论的审计（claim-level audit）；
- 不能对外说"numeric 92%"或"临床准确率 96.7%"。

**可能的追问**："会不会只是种子运气好？"（25/34 对 0/34 的效应量很大，第 9、12 阶段也有复现；更多种子列为下一步。）"效果是不是来自多出来的行数和训练步数？"（见第 15 阶段的 P1-RAW，它是一个只改标签的对照。）

## 12. Qwen3.5 轮（A100，单个种子）

**目标**：这个发现能不能推广到另一个模型家族？更新的基座是不是更好？

**适配上的事实**：
- 混合架构：Gated DeltaNet 和 full attention 按 3:1 组合；
- 工具调用用 XML 格式；每一轮 assistant 都带一个空的 think 块；
- LoRA 扩展到了线性注意力的投影层，共 30.5M 参数；如果只用原来的 7 个模块名，32 层里只有 8 层会被适配；
- 使用 flash-linear-attention 内核；
- 词表约 248k，原来是 152k。但这只让 lm_head 在每个 token 计算量中的占比多了约 3 个百分点；速度变慢主要是因为线性注意力、序列更长（XML 加 think 块），以及 `PARALLEL=1` 时和推理任务抢资源。

**证据**

| 配置 | P1 编造（调用中 / 正文中） | 完整输入时正确调用 | 有依据的工具题 | 自然 Q5 拒答 | 过度调用 | v1 numeric | 临床说明 |
|---|---|---|---|---|---|---|---|
| R0-Q35-4B | 3/34（3 / 0） | 30/34 | 53/55 | 5/7 | **50/188** | 17/50 | **12/55** |
| R0-Q35-9B | 14/34 | 29/34 | 48/55 | 3/7 | 38/188 | 23/50 | 25/49 |
| **A-Q35-4B filtered，ep2** | **29/34（1 / 28）** | 33/34 | 54/55 | **2/7** | 0 | **34/50** | 53/55 |
| A-Q35-4B filtered，ep1 | （没跑 P1） | — | 53/55 | **7/7** | 2 | 35/50 | 52/55 |

**解读**：
1. **只做过滤的失败模式在另一个模型家族上复现了**，而且模板、调用格式、GPU 都不同。模型甚至会写"Using calculate_bmi with these values (weight_kg=108.5, height_cm=162.0)… BMI 41.4"，**实际上根本没有调用工具**，等于在正文里伪造了一次工具调用（hallucinated tool call）。这触发了事先写好的条件：应当跑一组 Qwen3.5 的 relabel。
2. **训练越久，编造越多**：自然 Q5 的拒答在 ep1 是 7/7，到 ep2 只剩 2/7。
3. **零样本的 Qwen3.5 是更强的工具调用者**（53/55），但会过度调用（50/188），拒答更少，也很少说出 BMI 分类。
4. **SFT 后的 numeric 看起来更好**：v1 34/50 对 25/50，v2.1 0.96 对 0.80，train-fit 38/50 对 32/50。两个打分器结论一致，而且 v1 更倾向于漏判（false negatives），这让信号更可信。但仍需等审计结果。
5. 成本：63.3 分钟、11.3 GiB，A100 上并且有资源竞争，所以不能和 Qwen3 直接比较。

smoke 测试的记录：工具参数检查在一个英制样本（train_006）上没有通过，是手动放行的，已经记录。

**决策**：之后专注于 Qwen3.5。F 冻结作为对照，不再训练新的 Qwen3 模型。

## 14. Stretch A：第三个工具 `calculate_egfr`

**为什么选 A 而不是 B**：
- 现有证据说明，SFT 学会的是**分布内**（in-distribution）两个工具的使用策略，包括什么时候不该调用；
- Stretch A 检验的是这套策略能不能**迁移**（transferable）到新工具上，而且能复用同一套依据性和拒答的评估机制；
- Stretch B（参考资料查询）检验的是检索能力，属于另一类能力。

**数据上的事实**：
- 所有病历都能抽出年龄和性别；
- 表格里有肌酐的记录：train 350、val 40、test 82；
- **表格自带的 eGFR 和 CKD-EPI 2021 公式算出来的对不上**：差异中位数 26–37，只有约 9% 在 ±5 以内。所以只用表格里**没有** eGFR 的记录：164 / 19 / 31。

**设计**：
- 工具：`calculate_egfr(creatinine_mg_dl, age, sex)`，CKD-EPI 2021 公式，返回整数。
- prompt v1e：在 v1 里加一句点名新工具，和 v1 点名其他工具的写法对称。
- 实验组：
  - 零样本：只给 schema、schema 加 prompt、base 模型；
  - A-sft：加 52 条模板生成的样本，包括 40 条正样本、6 条删掉年龄的拒答样本、6 条删掉性别的拒答样本。
- 评估：19 条正样本加 19 条删掉年龄的探针，再加 core 的回归检查（regression），其中包括在表格已有 eGFR 时会不会多余地调用新工具（over-call）。
- 事先登记的标准：A-sft 端到端 ≥ 15/19；探针编造 ≤ 2/19；core 工具题 ≥ 53/55；P1 ≤ 1/34；过度调用 ≤ 1/21。

**审核**（委托 AI 审核，不是临床人员）：
- 独立重新抽取参数，并用另写的一份 CKD-EPI 实现重新计算，机械性问题为 0/19。例子：val_000 → 2.5 mg/dL、58 岁、女性 → 21.75 → 22 → G4。
- 审核中做的修改：
  1. 答案模板从"consistent with CKD stage"改为"KDIGO GFR category …, assuming stable kidney function"。原因是有 4 份病历描述的是急性或可能急性的肾损伤，其中 val_009 明确是 AKI；
  2. 删掉年龄后修正句子的语法。
- 打上的标签：4 条肾功能可能不稳定（non-steady-state）、1 条接近分界值（44.91）、3 条提到年龄但没给数值。19 条全部通过，哈希已冻结。

## 15. 第四波设计（wave 4 design）

**三个假设（hypotheses）**

| | 假设 | 检验方法 |
|---|---|---|
| **H1** | 改标的效果在 Qwen3.5 上也成立 | A-Q35-relabel 对 A-Q35-filter：比较 P1、完整输入时的调用、自然 Q5 |
| **H2** | 两者都用 relabel 数据时，Qwen3.5 的 numeric 强于 Qwen3 | 对 F 和 Q35-relabel 各 50 道 numeric 题做逐条审计 |
| **H3** | 工具能力可以迁移（Stretch A） | 19 + 19 条 eGFR 评估集 |

**决策（Wave4-Q1 到 Q5）**

1. **主要结果固定用 ep2**（primary endpoint），和 F 的规则一样。两个 epoch 都跑 P1，但只作诊断。如果 ep2 没通过，照实报告，绝不换成 ep1。
2. **门槛**（gate）：阈值和 F 冻结的那一套完全一样，但对照组换成同家族的过滤版模型，这样整个设计和"F 对 C"完全同构。和 F 的跨家族比较只作报告，不影响是否通过。
   - 通过：Q35-relabel 成为最终候选，也是 Stretch A 的基座；
   - 没通过：退回用 F。
3. **硬件**：A100，内核和 A-Q35-filter 一样；训练时 `PARALLEL=0`，独占 GPU，保证计时干净。P1-RAW 也在 A100 上跑，硬件差异在报告里说明。
4. **H2 的判定规则**：
   - 主指标：Qwen3.5 独对的题数多于 F 独对的题数，而且精确符号检验（exact sign test）双侧 p < 0.05。比如分歧题里 Qwen3.5 独对 10 题、F 独对 2 题，p = 0.039；
   - 非劣性（non-inferiority）：P1 编造 ≤ 5%；有依据的工具题 ≥ 52/55；完整输入时正确调用 ≥ 31/34；作业的其他指标不能全部变差；
   - 三种结论："更强"、"可能更强但证据不足"、"没有证据"。
5. **执行顺序和停止规则**（stop rules）：
   - 顺序：第 1 轮 → 打分和审阅 → 审计 → 第 2 轮（Stretch A）→ 冻结 test 清单 → 跑一次 test；
   - 门槛没通过：照实报告；
   - 一致性检查（parity）不一致：停止 Stretch A，先排查；
   - A-sft 损害了 core：最终模型仍然是不带 eGFR 工具的版本；
   - test 只跑一次。

**辅助对照（supporting controls）**
- **P1-RAW**：第一波的 raw 模型，和 F 一样是 2000 条、250 步、种子 42，只有那 78 条的标签不同。在 P1 探针上评估它，就是一个**只改标签**的对照（label-only control）。
- **一致性重跑**（parity regeneration）：Stretch A 改动了 `src/`，所以用新代码重跑 A-Q35-filter ep2 的 val，要求逐条一致。新代码保证 core 两个工具的 schema 逐字节不变（哈希仍是 `9eb098db…`）。

**test（方案 B）**：冻结的模型清单是 Q35-relabel、F、Q35-filter、R0-Q35-4B，只报告事先指定的指标。test 上自然 Q5 的确认只有 10 条，统计力不足，需要说明。

## 17. 打分器的问题：v1 和 v2.1 在 numeric 上各自怎么误判

**目标**：解释为什么 v1 和 v2.1 在 numeric 上的差异这么大。以 F 对 Q35-relabel 为例：v1 下是 58% 对 72%；v2.1 下是 46/50 对 46/50。

**两者怎么判 numeric**

- **v1**（`metrics.py:235`）**由 gold 驱动**（gold-driven）：
  - gold 答案里**计算出来的**数字（输入里没有的），都必须以 gold 的精度出现在预测中；
  - 同一句话里还要有相同的方向词。
- **v2.1**（`scorer_v2.py` 的 `build_key` / `run_check`）**由问题驱动**（question-driven）：
  - 根据问题的从句和从输入算出的值建立检查。val 的 numeric 一共 83 个检查，其中 39 个是差值；
  - 答案里只要有**任意一个**数落在容差带里就算通过；
  - 只检查问题问到的部分；val 的 50 道 numeric 里有 15 道的答案键只覆盖了一部分（partial）。

**证据：和盲评参考答案相比的误判数**（只统计两组评审意见一致的 numeric 样本）

| 验证集 | v1：误判为错误 / 误判为正确 / 一致 | v2.1：误判为错误 / 误判为正确 / 一致 |
|---|---|---|
| 开发集（调过规则） | 20 / 0 / 25 | 0 / 0 / 45 |
| holdout 1（调过规则） | 19 / 2 / 24 | 3 / 2 / 40 |
| **holdout 2（干净）** | **17 / 0 / 18（51%）** | **0 / 1 / 34（97%）** |

**v1 不适合用来判 numeric。** 它的误判几乎都是把写法不同的正确答案判错，例如：
- 用倍数代替百分比（val_047）；
- gold 顺带比较了其他指标，那个数字也被要求出现（val_186）。

Qwen3.5 的 SFT 输出更贴近 gold 的模板，所以它在 v1 下的领先被放大了。

**v2.1 为什么仍然判得太宽**：它从不检查答案里**多写的陈述**，答案里出现矛盾的数字也不会扣分。F ep2 有 3 条这样的误判为正确：
- val_117：写"ferritin … below by 4.2"，正确是 5.2；
- val_194：写"Creatinine is also elevated at 1.2"，其实在正常范围内；
- val_062：写"exceeds by 9 bpm (100 − 99 = 1)"。

盲评细则本身也不要求多写的陈述必须正确；而且几组 holdout 都来自第一波的模型，那批模型的错误主要出在被问到的部分。

**打分器的误差取决于被评的模型。** 模型越强，剩下的错误越会转移到 v2.1 看不到的多写陈述里。

我非正式地逐条读了 F 和 Q35-relabel 在 v1 下的 16 条分歧题：
- 大约 7 条是 Qwen3.5 真的对：val_001、062、085、117、185、194、202；
- 1 条是 F 真的对：val_114；
- 其余都只是写法不同。

**原型（prototype，没有采用）**：`scripts/scorer_v22.py` 在冻结的 v2.1 之上加了两条防护规则。只作用于 numeric 题，而且只会把"对"改成"错"。

两条规则：
1. 答案说某项指标异常，这个判断必须和输入一致；
2. "by X"或"X above/below the limit"里的数值，必须等于 |值 − 界限|。

结果：
- gold 自检 0/450 误报；
- 和盲评参考答案新出现 4 处不一致，逐条核对后全部是真实错误，只是宽松的细则没有算错；
- 在 val 的各组模型上翻转了 6 条，全部核对过，确实是错的；Qwen3.5 的几组没有任何变化；
- F ep2 的 numeric 从 46 降到 43；Q35-relabel 对 F 的符号检验是 5 对 2，p = 0.45。

**决策**：**报告仍然用 v2.1**，把这一点作为已知局限写进报告，v2.2 作为后续工作记录在案。理由有三：
- v2.2 没有干净的 holdout；
- 防护规则是在同一批数据上调出来的；
- numeric 的结论本来就以逐条审计为准。

详见 `reports/scorer_v2/VALIDATION.md` §5。

**可能的追问**
- "那 numeric 到底以哪个数字为准？" → 单靠任何一个打分器都不行：v1 判得太严，v2.1 对多写的错误陈述判得太宽。H2 由审计决定。
- "为什么不采用 v2.2？" → 它是在评估集上调出来的。采用它，就是重犯第 8 阶段 v2.0 的错误：相信一个只在自己的开发数据上验证过的打分器。

## 18. 当前结论、局限与下一步（claims, limitations, next steps）

**现在可以说的**（单个种子，val）：
1. 把输入不足的工具样本改标为显式拒答，可以消除缺测量值时的编造（25/34 → 0/34），而且不损害工具调用（54/55，完整输入时 33/34）。
2. 只做过滤会把编造从工具参数转移到正文里，而且在第二个模型家族上同样发生（29/34）。
3. 在工具使用上，SFT 明显优于 prompt 工程（54/55 对最多 29/55）；更严格的 prompt 和 8B 基座都解决不了依据性的问题。
4. 经过验证的 scorer 远比简单 scorer 可靠：在从未见过的 holdout 上，92.6% 对 65.7%。
5. 改标的效果在不同模型家族上都能复现（Qwen3.5：29/34 → 0/34）；只改标签的对照（P1-RAW，32/34）排除了"行数和训练时长"的解释。
6. 用同样的数据训练，两个基座打平（+0.25pp [−2.15, +3.10]）：数据策略的影响远大于换用更新的基座。

**现在还不能说的**：
- numeric 的准确率（等逐条审计；v1 判得太严，v2.1 看不到多写的错误陈述，见第 17 阶段）；
- Qwen3.5 更强（等 H2）；
- 总体意义上的编造率（0/34 的置信上限约 10%）；
- 结论对不同种子是否稳健；
- 一个干净的 test 估计。

**局限**：
- 只有一个种子；
- test 已经用过（第一波，以及验证 scorer 时）；val 被反复使用过；
- 评审是 LLM agent；人工抽查是非正式的；
- scorer 的两层解析都是正则，贴合模板；v2.1 在 numeric 上只检查问题问到的部分（见第 17 阶段）；
- 解释性的文字没有打分，这部分可能继承了 gold 风格带来的编造风险；
- 没有检验模型是照抄工具结果还是自己重算（tool-result faithfulness）；
- 数据是合成的、模板化的；
- 不同轮次之间存在硬件和代码版本的差异。

**下一步**（有更多时间时，按价值排序）：
1. 多跑几个种子（seeds）；
2. 建一份有记录的人工标注集，然后做"LLM 解析加确定性校验"的 scorer，再用人工标签训练校准过的裁判或 reward model。可以从 v2.2 的防护规则（第 17 阶段）起步，并在当前模型输出组成的新 holdout 上验证；
3. 篡改工具返回值的探针（tampered-tool-result probe）；
4. 用 MiniCheck 检查解释文字的依据性（groundedness）；
5. 补充"问题中不提缺失字段"的样本（R-IMPL）；
6. 推理可见化的消融（R-VIS）；
7. bf16 LoRA 和 QLoRA 的对照；
8. 8B 模型做 SFT，并重新调学习率；
9. 数据量曲线（data-size curve）；
10. 支持多次工具调用，比如先把 µmol/L 换算再算 eGFR；
11. 整理仓库：以 README 和 REPORT 作为评审的阅读路径，其余归档到 history。
